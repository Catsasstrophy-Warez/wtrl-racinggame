# WTRL Interaction Pattern Atlas — Recommendations for WTRL

## 0. What the atlas actually contains (read this before the rest)

`MASTER-ATLAS.md`, `Matrices/SCREEN-TO-SYSTEM-MATRIX.md`, and `Specifications/INTERACTION-SPEC-TEMPLATE.md` define a rigorous forensic method: for each of 25 real garage/racing games, decompose a screen into `intent → screen state → input → selection feedback → operation → consequence → test → persistence`, backed by frame-level video timestamps, and translate the result into a WTRL-specific SwiftUI/RealityKit/WTRLCore contract. That method is sound and worth keeping.

**But the 25 `Dossiers/*.md` files are unfilled templates, not completed research.** Every dossier has the same fixed skeleton with two pieces of real content: a one-line "primary domain" tag and a one-line "highest-value extraction" thesis (e.g. Wrench → *"Spatial service graph, fastener truth, tool gating"*). Every forensic section (S0–S6, the screenshot capture set, the acceptance tests) is still the generic instructional boilerplate, not an observed result. `Video_Ledger/VIDEO-TIMESTAMP-LEDGER.csv` confirms this directly: 20 of 25 rows are `SOURCE_SELECTION_REQUIRED` in every column — no source video has even been picked. The other 5 (CarX Drift Racing Online, No Limit Drag Racing 2, Mad Max, Crossout, and the screen-to-system matrix's own rationale rows) have a candidate video URL but every timestamp segment is `FRAME_REVIEW_REQUIRED` — meaning zero frames have actually been reviewed for any of the 25 games. There is no dossier in this tranche where a specific screen mechanic has been verified against footage.

This matters for how to read what follows. The screen-to-system matrix's "Selection feedback / Operation / Consequence" columns *look* like observed facts but are the same unverified one-line theses restated in table form, not independent evidence. Where I cite a dossier below, I am citing its filename and its thesis label (which is legitimate — it's the atlas author's selection rationale, and it correctly identifies which games are worth studying) — I am **not** claiming the atlas has verified how that game's UI actually works frame-by-frame, because it hasn't done that work yet. Where a recommendation below goes into specific mechanical detail (e.g. "CarX's dyno lets you retest without leaving the screen"), that detail comes from general knowledge of these well-known, publicly documented games, not from atlas evidence — and I've tried to keep that detail to things that are genre-uncontroversial rather than anything that would require a frame-accurate citation. **Before anyone treats a specific UI claim from this doc as settled, the underlying dossier still needs the frame-review pass the ledger is asking for.**

## 1. Garage (`GarageView.swift`)

Current shape: a single flat `List` — money/rep readout, an unordered `ForEach` of owned part names with no slot/category/install-state grouping, and two buttons to Dyno and Parts Shop. No visual distinction between "owned and installed," "owned and in the box," or vehicle identity.

- **Adopt: slot-grouped ownership list, not a flat name dump** (per the extraction theses of `05_Car_Mechanic_Simulator_2021.md` — "Readable repair workflow, shopping list, contextual modes" — and `13_Revhead.md` — "Grassroots economy and experimentation"). The concrete weakness: `GarageView.swift` lines 27–35 render `gameState.ownedParts` as bare `Text(part.name)` rows with no `slot` grouping, so a player with 6 owned parts can't tell what's installed on the current car vs. sitting unused. Scoped change: group the `ForEach` by `Part.slot` (data already exists — `installedComponents[String: [InstalledComponent]]` already keys by slot), and mark each row "Installed" / "In inventory" using the same boolean check `PartsShopView.swift` already computes at line 49. No new state needed, just a different `Section`/grouping in the existing `List`.
- **Adopt: garage as a car-identity readout, not just an economy readout** (thesis of `19_Mad_Max.md` — "Visible evolution, recipe builds" — and `10_Gran_Turismo_7.md` — "Lineage, car reverence"). WTRL's own `25-GARAGE-DESIGN.md` already specifies the garage as a diegetic, camera-station-based home screen with six functions (Store/Modify/Repair/Display/Trade/Generate) — the current `GarageView` is a placeholder list, not that design. The scoped, in-reach version for the current SwiftUI implementation (not the full spatial-station rebuild): add a header section showing `selectedVehicleID`, its installed-component count, and a one-line derived stat (e.g. current peak dyno power from `gameState.dynoRuns.last`) so the Garage screen answers "what car do I have and what does it do right now" before the player drills into Dyno or Parts Shop.
- **Do not adopt (yet): a walkable/spatial garage.** That's the correct long-term direction per WTRL's own `25-GARAGE-DESIGN.md` (camera-station model), but it's a RealityKit scene change, not a SwiftUI interaction-pattern change, and is out of scope for this recommendations pass — flagged here only so it isn't confused with the list-grouping change above, which is achievable today.

## 2. Dyno (`DynoView.swift`)

Current shape: already WTRL's best screen — sliders for 3 continuous calibration values, a deterministic `DynoSimulation.run`, a power curve `Canvas`, and a saved-run count. This is close to the atlas's own recommended "parameter → graph → decision" loop already.

- **Adopt: live/predictive curve preview before committing a Test Run** (thesis of `04_Automation.md` — "Parameter→graph→decision loop, dyno information architecture" — and `08_Forza_Motorsport.md` — "numeric ranges + explanations"). Concrete weakness: in `DynoView.swift`, `sliderRow` (lines 55–67) mutates `gameState.dynoFinalDrive` etc. immediately via the `Binding`, but the curve in `DynoCurveView` only updates when `runTest()` (line 68) is explicitly pressed and a full `DynoSimulation.run` completes — so dragging a slider gives zero visual feedback until the player taps "Test Run" again. Scoped change: keep `Test Run` as the canonical, persisted, WTRLCore-authoritative result (this matches WTRL's deterministic-physics-authority rule — no fudging), but add a lightweight, clearly-labeled "Preview" curve computed from the same `DynoSimulation` function on slider `.onChanged`, rendered in a dimmer color than the committed curve. This gives Forza/Automation-style immediate feedback without weakening "the dyno run itself is the only authoritative record" — the preview is explicitly not persisted or recorded via `recordDynoRun`.
- **Adopt: named/comparable saved runs** (thesis of `11_No_Limit_Drag_Racing_2.md` — "Dyno→tune→pass loop" — and `09_CarX_Drift_Racing_Online.md` — "Dense setup with immediate test path"). Concrete weakness: `gameState.dynoRuns` (an array, capped at 50 in `recordDynoRun`) is currently surfaced only as a count string ("`\(gameState.dynoRuns.count) run(s) stored`" — `DynoView.swift` line 41). The player can never look at run #3 again to compare it against the current curve. Scoped change: a `Picker` or small `List` of prior runs (labelled by slider values or index) that, when selected, overlays that run's curve semi-transparently behind the current one in `DynoCurveView` — pure UI, no new WTRLCore state, since `DynoRun.samples` already exists per run.
- **Do NOT adopt: dyno "upgrade parts" or shop items** — some of these games (Automation in particular) blend engineering-design and shop/economy screens. WTRL already deliberately separates the Dyno (free, continuous, no economy) from the Parts Shop (paid, discrete) per the comment at the top of `GarageView.swift` ("free calibration" vs. "paid, permanent") — keep that split; don't let Dyno acquire buy buttons.

## 3. Parts Shop (`PartsShopView.swift`)

Current shape: already implements the atlas's most common pattern — grayed-out-but-visible locked items showing price and rep requirement (`partRow`, lines 30–61) — this independently matches the thesis of multiple dossiers (`10_Gran_Turismo_7.md`, `16_Wreckfest.md`, `22_Need_for_Speed_Heat.md` all flag visible-but-locked catalog progression as their extraction). No change needed there; it's a case where WTRL already converged on the right pattern.

- **Adopt: fitment/compatibility feedback before purchase, not just rep/money gating** (thesis of `06_Street_Legal_Racing__Redline.md` — "vehicle/stat/fitment feedback" — and `19_Mad_Max.md` — "requirement/capability preview"). Concrete weakness: `partRow` computes `owned`, `repLocked`, `afford` but nothing about whether the part actually changes anything on the *currently selected* vehicle vs. a generic slot — a player buying a part sees only its static `effectSummary` string, never a before/after delta against their current car's dyno numbers. Scoped change: when `gameState.dynoRuns.last` exists for the selected vehicle, show a small "+X kW est." delta line under `effectSummary`, computed the same deterministic way Dyno already computes power — reuses `DynoSimulation`, no new subsystem.
- **Adopt: two-step buy-then-install made visually contiguous** (thesis of `12_Pixel_Car_Racer.md` — "large touch feedback" — relevant given WTRL also ships touch controls). Concrete weakness: currently, buying (`gameState.purchase(part)`) and installing (`gameState.install(partID:slot:)`) are two separate taps in the same row with no visual linkage beyond row state (lines 48–58) — a player who taps "$X" to buy doesn't see the row immediately offer "Install" without the whole `List` re-rendering the section. Since `owned` is already derived reactively from `@Bindable var gameState`, this mostly already updates instantly — the actual gap is that there's no confirmation feedback (haptic/visual pulse) marking the state transition, which several shop-pattern dossiers (`22_Need_for_Speed_Heat.md`, `10_Gran_Turismo_7.md`) flag as important for "did my purchase register" clarity. Scoped change: a brief `.transition`/scale animation on the row when `owned` flips true, no new state.
- **Do NOT adopt: blind gacha/loot-box-style part acquisition** — not present in any of these 25 dossiers' theses, but worth stating explicitly since "randomized part drops" appears in some mobile racing games' shops (Pixel Car Racer has gambling-adjacent minigames in its real design) — WTRL's no-pay-to-win rule rules this out categorically; the deterministic price/rep table already in `PartsCatalog` is correct and should not be replaced with randomized offers.

## 4. Diner (`DinerView.swift`)

Current shape: already minimal and correct per WTRL's own stated rule (see file header comment: "per the zero cutscenes rule, entirely skippable. No wrench minigames, no unskippable dialogue"). This is the one screen where the recommendation is almost entirely "preserve as-is."

- **Adopt (small): tie diner lines to more than reputation tier — surface recent-event context** (thesis of `10_Gran_Turismo_7.md`'s cafe-as-narrative-hub idea, filtered through WTRL's no-cutscene rule). Concrete observation: `Mentor.swift`'s `dinerLines(for:)` (lines 44–67) is keyed only on `ReputationTier`, so the diner says the same small pool of lines regardless of what the player just did (won an outrun, failed a license test, etc.) — `MentorContext.dinerIdle` doesn't take any event parameter. Scoped change: extend `dinerLines` to also branch on `gameState.hasWonOutrun`/`gameState.licensePassed` flags already in `GameState`, still zero new UI, still text-only, still skippable — this is a data-shape change to an existing `enum`/`switch`, not a new screen or interaction.
- **Do NOT adopt: any dossier's "walk around and interact with objects" diner/cafe pattern** (e.g. anything resembling My Garage's or Pacific Drive's first-person interaction model, or a GT7-style multi-tab cafe menu). WTRL's Diner is explicitly the anti-example of that — the file comment states it's "cheaper than a dedicated cafe scene" — adopting a richer interactive diner would directly contradict the zero-cutscenes/no-minigame rule stated in the file itself.

## 5. Gas Station (`GasStationView.swift`)

Current shape: single button, single price, no state beyond `money -= 40`.

- **Adopt: fuel as visible car state, not an instant abstract deduction** (thesis of `17_SnowRunner.md` — "preparation as gameplay" — and `07_Pacific_Drive.md` — "diegetic station feedback"). Concrete weakness: `GameState.refuel()` (lines 73–76) has no fuel-level state at all — `money` just decreases; there's no `fuelLevel` field to refuel *into*, so the screen has no feedback loop (nothing shows "empty" before or "full" after). This is arguably a missing WTRLCore concept, not just a missing UI element — flagging it for scoping rather than recommending it outright, since adding a fuel-consumption simulation is a design decision beyond this UI-recommendations doc's scope, not a small UI tweak. If WTRL doesn't intend fuel to matter mechanically (a valid choice — plenty of arcade racers don't model it), the current single-button screen is already appropriately minimal and doesn't need atlas patterns applied to it.
- **Do NOT adopt: SnowRunner/Expeditions-style deep logistics loadout screens at the gas station** — WTRL's gas station is a landmark/refuel point per its own file comment ("social/navigation landmark cheap enough to place liberally"), not a preparation hub; that job belongs to Garage/Dyno/Parts Shop. Keep it minimal.

## 6. HUD / driving (`HUDView.swift`)

Current shape: top bar (camera/money/rep/lap or waypoint info), POI interaction prompt, bottom bar (camera/race-toggle buttons + a full keybinding legend string always on screen).

- **Adopt: minimal-HUD-by-default with progressive disclosure, not a permanent keybind legend** (thesis of `24_Absolute_Drift.md` — "Low-clutter motion/score feedback" — directly applicable since WTRL already has an `H = hide HUD` toggle, i.e. it already knows clutter is a concern). Concrete weakness: `bottomBar` (lines 115–137) always renders the full string `"WASD / arrows to drive · Space = handbrake · E = interact · L = license test · O = outrun · H = hide HUD"` regardless of `hudHidden` state or how long the player has been driving — this is permanent onboarding text with no fade-out. Scoped change: fade/remove the legend text after N seconds of `raceElapsedSeconds` or first-successful-interact, independent of the existing `hudHidden` toggle (which should stay as a manual full-HUD-off option) — pure `GameState`-driven `.opacity`/timer logic in the existing `bottomBar` view.
- **Adopt: outrun gap readout styling matches drag-hud conventions** — already partially true (`gameState.outrunGapMeters` colored green/red at lines 12–23) — the one gap versus the `11_No_Limit_Drag_Racing_2.md` thesis ("full drag ritual") is that there's no launch/reaction-style pre-run state; this is noted for completeness but is a race-format design question (already covered by `41-RACE-FORMATS-GHOSTS-OBJECTIVES.md`'s Outrun format spec) rather than a HUD-file change, so no concrete Swift change is proposed here.
- **Do NOT adopt: BeamNG-style live telemetry/damage overlay graphs during free-roam** (thesis of `03_BeamNG_drive.md` — "debug visualization"). BeamNG's dossier thesis is explicitly a *debug* visualization pattern; permanently exposing that much numeric detail during ordinary driving would conflict with the Absolute-Drift-style low-clutter direction recommended above and isn't something any of the 25 dossiers' theses actually recommend for normal play (only for tuning/dyno contexts, which WTRL already handles in `DynoView`).

## 7. Touch controls (`TouchDriveControls.swift`)

Current shape: hold-buttons for left/right/brake/accelerate, tap buttons for up/downshift, all `.borderedProminent` in one `HStack`.

- **Adopt: larger, thumb-zone-anchored hit targets and asymmetric button sizing** (thesis of `12_Pixel_Car_Racer.md` — "Small-screen engineering, clutch/manual-shift controls" — the one dossier in this set whose domain is explicitly mobile touch driving controls). Concrete weakness: every button in `TouchDriveControls.swift` (lines 6–19) uses the same default `Button` sizing inside a plain `HStack`, with no explicit frame/hit-area sizing — accelerate/brake (the highest-frequency inputs) get the same tap target as up/down shift (lower-frequency). Scoped change: give `hold("GO", .accelerate)` and `hold("BRAKE", .brake)` an explicit larger `.frame(minWidth:minHeight:)` than the shift buttons, and anchor them to the screen's bottom corners (thumb zones) rather than a centered `HStack` — a `ZStack`/`GeometryReader`-based layout change, not new input logic.
- **Adopt: pressed-state visual feedback distinct from `.borderedProminent`'s default** (same Pixel Car Racer thesis — "large touch feedback"). Concrete weakness: `hold()` (lines 20–25) drives `input.keyDown`/`keyUp` off a `DragGesture(minimumDistance: 0)`, but nothing in the view reacts to the gesture's active state — the button doesn't visually indicate "currently held" beyond SwiftUI's default press-highlight, which is easy to miss mid-race. Scoped change: track a local `@State` per-button (or a small set of currently-held commands read from `input`) and apply a scale/brightness change while held — cosmetic, additive to the existing gesture handler.
- **Do NOT adopt: on-screen steering wheel or tilt-steering** — no dossier here documents that as a strength (Hill Climb Racing 2's thesis is explicitly "control economy" via two taps, not a wheel), and WTRL's existing discrete left/right hold-buttons already match the simpler, more proven pattern; don't add complexity the atlas doesn't support.

## 8. Patterns from the atlas WTRL should explicitly NOT adopt

These matter as much as the "adopt" list, because several atlas games' central mechanics directly conflict with rules WTRL has already decided:

- **Any cutscene, unskippable dialogue, or blocking narrative sequence** — several dossiers' domains (`10_Gran_Turismo_7.md` "culture/reverence", `19_Mad_Max.md` "visible evolution") come from games that use cinematic reveal sequences for car customization or story beats. WTRL's `DinerView.swift` and `Mentor.swift` file comments are explicit: "zero cutscenes," "never a cutscene, never blocking." Do not adopt any reveal-cinematic pattern regardless of how good it looks in the source game.
- **Fudged/non-deterministic outcome resolution** — `03_BeamNG_drive.md`'s thesis is "causal physics, consequence-first design," which is actually aligned with WTRL, but other arcade-leaning games in this set (Need for Speed Heat, Hill Climb Racing 2) are known for rubber-banding, scripted rival behavior, or forgiving hit-detection that isn't strictly simulation-driven. WTRL's Dyno (`DynoSimulation.run`) and its "deterministic dyno" section header already commit to simulation authority — any atlas pattern that implies a UI-layer or scripted override of a simulated result (e.g. a guaranteed-win outrun animation) should not be adopted.
- **Pay-to-win acceleration of the two-axis money/reputation gate** — several shop-pattern games in mobile/live-service adjacent genres (the domain tags for `12_Pixel_Car_Racer.md` and `22_Need_for_Speed_Heat.md`) come from monetization contexts where currency can be bought or reputation-equivalent progress can be skipped for cash. WTRL's `PartsShopView.swift` gating (`repLocked`/`afford`, both derived purely from gameplay-earned `money`/`reputation`) must stay closed to any real-money or skip-the-grind pattern.
- **Merging money and reputation into a single meter or a single unlock currency** — this is the opposite direction from `48-RPG-SYSTEMS-SPEC.md`'s explicit two-axis design (money buys what's shown; reputation decides what's shown at all) and from the comment already in `PartsShopView.swift` ("kept genuinely separate rather than merged into one meter"). No atlas game's economy pattern should be adopted if it collapses these back into one number.
- **Spinner/loading-screen part installation** — `25-GARAGE-DESIGN.md` explicitly states "never show a spinner" for install sequences, favoring vignette animation instead. Some of the construction/attachment games in this set (Crossout, Trailmakers — domain "construction") use instant snap-and-done part placement with no install ceremony at all, which is fine, but any pattern from a menu-driven mechanic-sim (Car Mechanic Simulator, Wrench) that resolves installs via a progress-bar/loading-spinner should not be copied literally.

## 9. Prioritized shortlist (5–8 scoped changes, effort/impact ordered)

1. **Dyno: live preview curve on slider drag** (Section 2) — small, additive, reuses `DynoSimulation` and existing sliders; highest ratio of "feels dramatically better" to "lines touched" in `DynoView.swift`.
2. **Garage: group owned parts by slot + installed/uninstalled state** (Section 1) — pure `List`/`ForEach` restructuring in `GarageView.swift`, no new state, fixes a real readability gap using data (`installedComponents`) that already exists.
3. **Touch controls: asymmetric hit-target sizing for accelerate/brake** (Section 7) — layout-only change to `TouchDriveControls.swift`, directly improves the mobile control-economy weakness the atlas's one mobile-domain dossier (Pixel Car Racer) calls out.
4. **HUD: fade the permanent keybind legend after onboarding** (Section 6) — timer/opacity logic added to existing `bottomBar`, addresses HUD clutter WTRL already cares about (it already ships an `H` hide-toggle).
5. **Touch controls: pressed-state visual feedback on hold-buttons** (Section 7) — small `@State`-driven cosmetic change to `hold()`, cheap confidence-of-input win on mobile.
6. **Parts Shop: dyno-delta preview on part rows** (Section 3) — moderate, requires wiring `DynoSimulation` into `PartsShopView`, but turns an abstract `effectSummary` string into a concrete number, addressing the single dossier-supported fitment-feedback gap.
7. **Diner: branch mentor lines on recent event flags, not just reputation tier** (Section 4) — small `enum`/`switch` extension in `Mentor.swift`, keeps the zero-cutscene rule intact while making the diner feel reactive rather than static.
8. **Dyno: comparable/overlay prior runs** (Section 2) — largest of the eight (needs a run-picker UI plus overlay rendering in `DynoCurveView`), but unlocks the "tune → test → compare" loop several of the atlas's engineering-domain dossiers (Automation, No Limit Drag Racing 2, CarX) converge on as their thesis, even though none of those three theses have been frame-verified yet.

**Caveat carried through the whole list**: none of the eight items above depend on any atlas dossier's *unverified* frame-level claims — each is justified primarily by a concrete weakness found directly in WTRL's current Swift source, with the dossier thesis label cited as directional precedent rather than proof. If the atlas team completes frame review on any of the 5 dossiers that already have a candidate video (CarX, No Limit Drag Racing 2, Mad Max, Crossout, and none currently for the rest), this document should be revisited — a verified frame decomposition could sharpen or contradict the general-knowledge detail used above.
